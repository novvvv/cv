## 자체 로그인 vs Firebase

냐키의 기능을 대부분 구현한 뒤, 실제로 유저를 받기 전에 로그인 기능을 구현하고자 한다.
회원가입/로그인 페이지를 만들면서 법적으로나 사용자 관점에서나 생각해야 할 부분이 많다고
판단되어 글로 작성해 둔다.
개인 소규모 앱 구현 측면에서 가장 먼저 고려해야 할 부분이 자체 로그인 vs 대행 서비스 사용이다.

대부분의 1인 개발 서비스에서는 자체 로그인 기능을 붙이지 않는 쪽이 대세이다.
자체 로그인 개발 자체가 어려워서가 아니라, 법과 책임의 문제 때문이다.
비밀번호를 직접 보관하는 순간 개인정보처리자가 되며, 개인정보 처리방침 고지, 보관/파기 의무,
안전성 확보조치 기준(암호화, 접근통제, 접속기록 보관)이 따라붙는다. 유출되면 신고 의무와
과징금이 있다.
반면 소셜 로그인만 사용하면 해당 리스크를 떠안을 이유가 사라진다.

기술적으로도 만들 것이 적지 않다. 비밀번호 해싱은 그중 하나일 뿐이다.

- 비밀번호 해싱: Argon2id 또는 bcrypt. SHA-256 같은 빠른 해시는 틀린 답이다
- 로그인 실패 rate limit, 계정 잠금
- 타이밍 공격 방지. 계정이 없어도 더미 해시를 검증해 응답 시간을 맞춰야 한다
- 이메일 열거 방지
- 이메일 인증/비밀번호 재설정 토큰 (단일 사용, 해시해서 저장, 만료)
- refresh 토큰 발급/회전/재사용 탐지
- 소셜 OAuth 직접 구현 (state, PKCE, nonce)
- 메일 발송 인프라. SPF/DKIM을 안 맞추면 스팸함으로 간다

혼자 만드는 서비스에서 이걸 전부 제대로 해두는 건 몇 주짜리 일이고, 하나라도 빠지면
위임했을 때보다 나쁜 보안이 된다.

그래서 보통은 Firebase + 소셜 로그인(Google/Apple/Kakao)을 붙이는 경우가 대다수이다.
단, iOS에 애플리케이션을 낸다고 하면 애플 심사 지침 4.8에 따라 서드파티 소셜 로그인을
제공할 경우 반드시 Sign in with Apple도 같이 제공해야만 심사가 통과한다.
따라서 Nyaki web site도 Firebase 기반 OAuth를 도입하고, 추후에 사용자 규모가 커졌을 때
자체 로그인 도입 전환을 고려할 예정이다.

## Firebase의 장점

- 비밀번호 해싱
- 로그인 rate limit
- 이메일 열거 방지
- refresh token 회전

위와 같이 자체 로그인을 도입했을 때 고려해야 하는 다양한 보안적 요소를 해결해준다.

이메일 열거 방지는 없는 계정과 틀린 비밀번호에 같은 오류를 돌려주는 것을 말한다.
아무 주소나 넣어보며 "이 사람이 가입했구나"를 알아내는 걸 막는 장치다. 요즘 생성한
프로젝트는 기본으로 켜져 있어서 두 경우 모두 `auth/invalid-credential`이 온다.

refresh token 회전은 갱신할 때마다 새 refresh 토큰을 주고 이전 것을 폐기하는 방식이다.
같은 토큰이 두 번 쓰이면 탈취로 보고 끊는다. Firebase ID 토큰의 수명이 1시간으로 짧은
것도 같은 맥락이고, 갱신은 클라이언트 SDK가 알아서 한다.

단, Firebase 도입을 진행했더라도 아래와 같은 부분은 고려해야 한다.

1. check_revoked = True (안 켜면 로그아웃하더라도 토큰이 최대 1시간 동안 산다)
2. API rate limit
3. 데이터 격리

### 1. check_revoked

이 문제를 부르는 이름은 토큰 폐기(token revocation)이고, stateless JWT의 알려진
트레이드오프다. 서버가 세션을 들고 있지 않고 토큰의 서명만 검증하기 때문에, 로그아웃을
눌러도 이미 발급된 토큰을 끊을 방법이 기본적으로 없다. 세션 방식이라면 서버에서 세션을
지우는 것으로 끝나는 일이다.

해법은 대개 셋 중 하나다. 액세스 토큰 수명을 짧게 두거나, 폐기 목록(denylist)을 두고 매
요청 조회하거나, 발급자에게 물어보는 것이다. Firebase는 세 번째를 제공한다. Admin SDK의
`verify_id_token(check_revoked=True)`를 쓰면 폐기 여부까지 확인한다. 기본값이 `False`라
명시적으로 켜야 하고, 켜면 Firebase 조회가 한 번 더 들어간다. 로그아웃과 회원 탈퇴를 즉시
반영하려면 이 비용을 내야 한다.

### 2. API rate limit

Firebase가 막아주는 것은 로그인 시도다. 내가 만든 `/v1/words`를 초당 수천 번 때리는 것은
전혀 다른 문제이고 내 서버 몫이다. 리버스 프록시(Caddy, Nginx) 레벨에서 IP당 제한을 거는
것이 가장 싸게 먹힌다.

### 3. 데이터 격리

토큰 검증은 "이 사람이 누구인가"까지만 답한다. "이 데이터를 볼 자격이 있는가"는 전적으로
내 코드의 일이다.

냐키는 모든 테이블에 `user_id` 컬럼을 두고 `(id, user_id)` 복합 기본키로 격리한다.
중요한 것은 `user_id`를 요청 본문이 아니라 토큰에서 서버가 직접 꺼낸다는 점이다.
클라이언트가 남의 id를 적어 보낼 자리를 아예 만들지 않으면 IDOR이 구조적으로 생기지 않는다.

## Firebase 제약

- 토큰이 XSS에 노출된다. Firebase JS SDK는 인증 상태를 IndexedDB에 두기 때문 (httpOnly 쿠키가 아님)

쿠키 세션으로 바꾸면 XSS에는 강해지지만 CSRF 대비가 새로 필요하고, 모바일 앱과는 잘 맞지
않는다. 냐키는 Flutter 앱이 같은 API를 쓰기 때문에 `Authorization: Bearer` 헤더 방식을
택했고, 이 경우 CSRF는 구조적으로 발생하지 않는다. 어느 쪽을 택해도 하나는 포기하게 된다.

## 정리

인증을 위임한다는 것은 안 만든다는 뜻이 아니라 경계를 긋는 일이었다. 신원 확인과 비밀번호
보관, 토큰 발급과 갱신은 Firebase가 하고, 내 서버는 토큰을 검증해 사용자 id를 꺼내는 것과
그 id로 데이터를 가르는 일을 한다.

이렇게 나눠두면 나중에 자체 구현으로 옮기더라도 고칠 곳이 토큰을 검증해 사용자 id를
돌려주는 함수 하나로 모인다. 그 함수의 계약만 지키면 나머지 도메인 코드는 인증 방식이
무엇인지 알 필요가 없다.
